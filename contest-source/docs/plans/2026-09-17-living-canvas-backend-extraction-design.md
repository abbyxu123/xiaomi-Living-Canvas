# 画间独立决策后台抽取设计

## 目标

把旧原型中已经验证过、且画间确实需要的决策能力抽取到比赛仓库，形成
`Living Canvas Decision Backend（画间决策后台）`。最终项目必须可以只依赖
当前仓库完成开发、测试与演示，不再依赖桌面上的旧原型目录。

## 品牌与命名边界

- 产品、源码文件名、模块名、环境变量、日志、测试、脚本和文档统一使用
  `Living Canvas`、`living_canvas` 或“画间”。
- 会话参数使用 `session` 或 `session_id`，不保留旧项目的简称。
- 比赛仓库增加命名门禁；对当前受版本控制的文件做不区分大小写扫描，旧名称
  出现即测试失败。
- 旧原型只作为本地迁移参考，不进入运行路径、提交包或比赛材料。
- 不迁移旧 UI、旧角色图片、旧硬件固件、旧训练集、历史数据库、用户数据、
  私密工程资料或本地凭据。

## P0 功能边界

新后台只实现比赛主链路需要的能力：

1. Gemini S1 创建会话。
2. 接收人数、预算、时限、口味、忌口与外卖需求。
3. 主 Agent 在硬约束内选择一个候选；MiMo 不可用时走确定性规则。
4. 比格犬作为“协调与执行”前台角色展示过程，美短猫提供口味记忆与反馈视角。
5. 用户在画框上二次确认后，后台只生成白名单外卖搜索链接，不自动下单、不付款。
6. 板端显示短二维码，手机进入画间确认页继续核对。
7. 手机评价写入画间自己的可删除本地记忆。

天气、宠物快报、食材识别、营养、盲盒扩展、语音识别、视频播放和传感器均不阻塞
P0，但数据契约为鸽子、小猪和外星人的后续表达角色保留扩展位置。

## API 与数据流

保留已经由 Gemini S1 合同使用的通用端点：

- `GET /health`
- `POST /v1/session`
- `POST /v1/input`
- `POST /v1/device/event`
- `POST /v1/confirm`
- `POST /v1/feedback`
- `GET /c/{token}`
- `GET /console?session=...`

`/v1/input` 必须同时接受结构化约束和自然语言。硬约束永远由本地代码复核，模型
只能提供结构化建议和软评分。确认前不生成外部动作；确认后也只返回平台搜索页，
付款仍由手机上的用户完成。

## 角色与 Agent 关系

系统只有一个持有任务状态和工具权限的主 Agent。五个角色是画面表达视角：

- 比格犬：当餐协调、执行与确认。
- 美短猫：口味记忆与反馈。
- 鸽子：天气和轻提醒。
- 小猪：食材与轻营养。
- 外星人：探索尝新与盲盒。

后台不得把角色数量伪装成多个独立自治 Agent，也不得复用旧原型的角色文案。

## 迁移方法

不复制旧入口文件。先为画间定义测试和新模块接口，再逐项移植经过验证的算法：

- 数据字段与状态机概念可以保留，但模块和注释重新命名。
- 硬约束、评分和审核逻辑按测试逐段迁移。
- 模型适配层只保留通用 OpenAI 兼容调用，不迁移旧训练支线。
- 手机页重新制作最小画间版本，不复制旧 HTML/CSS/图片。
- 候选数据重新整理为画间演示数据，不迁移历史账本。

## 测试与验收

- 新后台单元测试覆盖硬约束、规则降级、确认门、白名单链接和可删除记忆。
- FastAPI 集成测试覆盖“创建会话 → 推荐 → 二次确认 → 手机接力 → 反馈”。
- 现有 Gemini S1 C 测试改用 `lc_backend_contract`，全部继续通过。
- 现有实网验证脚本改名并只启动当前仓库内的新后台。
- 命名门禁证明受版本控制文件中没有旧项目名称或旧模块前缀。
- 最终在 Ubuntu/openvela 中重新构建，并在真机扫码后才宣称端到端完成。

## 风险与处理

- **复制过多导致新项目仍像旧项目：** 以 P0 API 测试为迁移白名单，未被测试需要的
  文件不进入新仓库。
- **模型不可用：** 确定性规则始终可给出一个受约束候选，并明确标记降级。
- **演示候选与真实商家不一致：** 只把候选当菜品方向，手机端打开真实平台搜索页，
  不声称库存、门店或配送时间已经核实。
- **历史提交仍含旧名称：** 当前功能稳定后创建干净的比赛集成提交，不删除现有本地
  安全分支，避免丢失工作。
